# 产研文档维护与编辑 Skill：设计说明

日期：2026-09-16

## 目标与边界

本 Skill 面向 PRD、技术方案、架构方案、技术设计、接口说明、项目交付文档和架构决策记录的维护与编辑。优先覆盖补写、润色、局部重构、评审意见落实和跨章节一致性修订；支持新建文档，但不扩展成通用办公自动化平台。

Skill 负责内容纪律、编辑流程和平台能力选择，不复制具体平台接口。飞书在线文档复用 `lark-doc`，飞书原生 Markdown 复用 `lark-markdown`，ADR 与术语治理复用 `domain-modeling`。本地 Markdown 使用运行环境已有的文件工具；其他平台先核实实际能力。

安装位置为 `/home/littlekey/.agents/skills/maintaining-product-engineering-docs/`。按用户确认，OpenCode 与 Codex 均从该共享目录发现 Skills，不创建额外副本或符号链接。

## 主要失败模式与对应设计

| 失败模式 | 预防设计 |
|---|---|
| 把“保留这段”“已删除”等协作过程写入正文 | 将候选正文、修改摘要、待澄清问题设为三个逻辑通道；只把候选正文交给写入操作；使用精确污染短语检查而非关键词封禁 |
| 将合法需求“用户可删除记录”误判为过程污染 | 不禁用“用户”“删除”“保留”等单词；脚本只提示高置信度过程短语，最终由语义判断确认 |
| 局部润色演变为全文改写 | 先确定变更层级和目标锚点；默认采用满足目标的最小修改，并对非目标区域做范围检查 |
| 同名标题或重复文本导致误改 | 使用章节路径、邻近文本、块标识或唯一内容组合定位；写入前验证目标唯一性 |
| 样式或图片、画板、嵌入表格等资源受损 | 纯文本读取不得视为完整样式；先核实平台的结构与资源能力，能力不足时缩小修改范围，写后回读并在可用时视觉核验 |
| 参数更新后验收指标、接口或交叉引用未同步 | 最小修改包含必要联动检查，不等于只改一个位置 |
| 建议被写成已确定决策，或模板诱发虚构事实 | 显式区分事实、建议、待决策、假设与未知；冲突影响结果时提问，缺失信息不得编造 |
| 超时、部分成功或并发编辑造成重复插入/覆盖 | 非幂等重试前重新读取当前状态；比较版本或目标快照；验证部分成功范围后再继续 |
| 工具返回成功却未形成合格文档 | 写入后必须回读受影响范围；视觉能力可用时复杂渲染必须做视觉核验，结构检查只能补充不能替代；视觉能力不可用时如实声明该限制 |

## 结构与加载策略

`SKILL.md` 是简洁路由器，只包含触发边界、核心流程、风险升级条件和 references 加载表。详细材料按需拆分：

- `content-boundaries.md`：正文边界、正反例、三通道隔离。
- `editing-workflow.md`：按风险伸缩的读取、计划、执行、重试与验证流程。
- `document-type-checklists.md`：各类文档的检查维度，不强制新增目录。
- `platform-adaptation.md`：平台能力核实、飞书 Skill 复用、本地 Markdown 与其他平台策略。
- `evaluation-cases.md`：13 个评估用例，每例包含输入、预期、失败条件、验证方式。
- `usage-examples.md`：日常触发示例。

`scripts/validate_candidate.py` 仅执行确定性检查：精确必需/禁用文本、预期出现次数、高置信度过程污染短语，以及可选的 Markdown 图片、链接、引用等资源标记保留检查。它不判断事实真伪、决策状态或富文本保真，也不作为发布入口。`scripts/test_validate_candidate.py` 用真实正反场景验证校验器不会机械误伤合法产品表述。

## 工作流

1. 确认文档类型、读者、目标、范围和受保护内容；上下文充分时不重复询问。
2. 小任务读取目标及邻近上下文；大文档先读目录，再定位章节；按风险读取结构、样式、资源和关联内容。
3. 内部形成目标位置、候选修改、联动位置和验证方式；仅关键歧义或不可恢复操作需要确认。
4. 生成独立候选正文，并预检过程污染、事实状态、修改范围、结构和资源风险。
5. 使用平台支持的最小可行操作；依赖内容按顺序修改；冲突或不确定结果先回读再决定。
6. 写入后回读受影响范围，检查落地、重复、遗漏、格式变化、资源与必要联动。
7. 在聊天中简述完成内容、实际验证和遗留限制，不把反馈写入正文。

## 关键取舍

- 选择“轻量主 Skill + 按需 references”，避免每次触发加载所有案例和平台细节。
- 选择复用既有平台 Skills，不维护第二套飞书命令或作出无损编辑保证。
- 选择逻辑隔离而非统一发布器；没有程序化发布入口，因此明确不宣称强制隔离。
- 选择保守、可解释的确定性校验；语义、事实和平台保真仍由模型判断与实际回读承担。
- 不强制统一文档模板。文档类型清单是检查维度，现有模板和用户明确要求优先。

## 验证策略与能力边界

实施后运行 Python 标准库测试，覆盖污染短语、合法“用户可删除”表述、重复插入、精确约束和 Markdown 资源标记。随后检查 Skill frontmatter、相对链接、文件完整性和脚本帮助信息。

没有真实文档时，不声称完成飞书富文本保真实测。最小后续实测应包含：带加粗和链接的段落局部修改、表格单元格补写、含图片/画板/嵌入表格的章节局部修改、以及超时或并发变更后的回读与防重复处理。
